## 0. 优先级判定标准（已确认）

| 级别 | 定义 |
|---|---|
| **P0** | 首版闭环必须满足。缺少它会使「导入数据 → 执行评测 → 查看得分与 Badcase Diff」核心链路**无法成立** |
| **P1** | 显著提升工程效率（双版本并排对比、CI Webhook、成本对账等），核心跑通后紧接着实现 |
| **P2** | 锦上添花或低频场景。**当前阶段不做界面，仅留底层字段扩展性** |

## 1. P0 闭环链路自检

P0 的故事必须能拼出这条不断链的路径：

```
US-015 配好模型网关凭证
   ↓
US-001 导入评测集 → 产生不可变版本 ED-02
   ↓
US-002 查看版本与 Case 明细，确认数据可信
   ↓
US-005 建 Target（T1：Prompt 模板 + 模型）→ 快照 ED-05
   ↓
US-003 / US-004 配置规则算子与 LLM 裁判算子 → 快照 ED-04
   ↓
US-006 发起 EvalRun（版本 × Target × 算子）并发执行 → ED-06
   ↓
US-007 SSE 实时进度与单条耗时
   ↓
US-008 单次运行报告：总分 / 各项指标 / 耗时 / Token 成本
   ↓
US-011 Badcase 双栏 Diff 抽屉：定位退化原因
```

> 链上任一环缺失即 P0 不成立。**反过来，链外的故事都在 P1 / P2。**

## 2. ROLE-A · AI / 算法研发工程师

### US-001 · 评测集导入与不可变版本快照

- **故事**：作为 ROLE-A，我希望在拿到一份评测数据（JSONL / CSV）时，把它**导入成为一个不可变版本**，从而让后续所有评测结果都能追溯到这份固定数据。
- **优先级**：`P0`（`已确认`）
- **理由**：PT-1 可追溯的起点；缺它则后续一切都是沙上建塔。也是 US-006 的硬前提。
- **依赖**：`case_key`、`schema_version="1"`、`content_hash`、`case_count`（见 `product-overview.md` §7）

### US-002 · 浏览评测集与版本历史

- **故事**：作为 ROLE-A，我希望在选数据集时能**看到名字、各版本号、条目数、创建时间与来源**，并点开任一版本查看**逐条 Case 明细**，从而在发起跑批前确认这份数据是我要的那一版。
- **优先级**：`P0`（`已确认`）
- **理由**：不确认数据就发跑批，是最贵的浪费（跑批要烧 Token）。且「版本不可变」若无界面呈现，用户无法建立信任。
- **依赖**：ED-01 / ED-02 / ED-03

### US-003 · 配置确定性规则算子

- **故事**：作为 ROLE-A，我希望在创建评测任务时**勾选并配置确定性规则算子**——`Recall@K`、`MRR`、`nDCG@K`、`JSON Schema 校验`、`正则匹配`、`精确数值保真度`，并设置各自参数（如 K 值、Schema 内容、数值容差），从而让可客观判定的部分用零成本、可复现的规则来打分。
- **优先级**：`P0`（`已确认`）
- **理由**：这是评测中台区别于「聊天打分器」的核心；规则算子成本为 0 且结果确定性，是 LLM 裁判不可替代的底座。
- **依赖**：`retrieval.relevant`（否则三个检索算子无法计算）、`reference.reference_facts`（数值保真）
- **备注**：算子参数的实例在 EvalRun 创建时**快照**（ED-04）。

### US-004 · 配置 LLM-as-a-Judge 裁判算子

- **故事**：作为 ROLE-A，我希望在创建评测任务时新增一个**裁判算子**：选择裁判模型、编写打分 Prompt 模板（可含评分维度与扣分标准）、设定分值区间与阈值，从而让开放式回答（相关性、忠实度、完整性）也能被量化。
- **优先级**：`P0`（`已确认`）
- **理由**：规则算子只能覆盖客观项，开放式生成质量必须靠裁判；这是产品的一半卖点。
- **依赖**：US-015（裁判模型凭证）
- **备注**：裁判成本口径见 `product-overview.md` `OPEN-3`（**未决**）。

### US-005 · 创建待测目标 Target（T1 平台内执行）

- **故事**：作为 ROLE-A，我希望在要测 Prompt 或换模型时，**创建一个 Target**：选定模型、填入 Prompt 模板与变量映射、设定温度与最大输出长度，从而让平台能替我实际发起调用并拿到输出。
- **优先级**：`P0`（`已确认`）
- **理由**：T1 是首版唯一执行方式（见 `product-overview.md` §4），没有 Target 就没有「被测对象」。
- **依赖**：US-015、ED-05

### US-006 · 发起 EvalRun 并发执行

- **故事**：作为 ROLE-A，我希望在改完 Prompt / 换完模型后，**选择「评测集版本 × Target × 算子组合」一键发起评测**，平台按设定的并发数自动跑完全部 Case，从而不必逐个手工调用。
- **优先级**：`P0`（`已确认`）
- **理由**：核心链路的执行段。并发是「3 分钟内出结果」的唯一手段。
- **依赖**：US-001（版本）、US-005（Target）、US-003/004（算子）、ED-06

### US-007 · SSE 实时查看进度与单条耗时

- **故事**：作为 ROLE-A，我希望在跑批过程中**实时看到已完成 / 总数、成功 / 失败条数，以及每条 Case 的耗时**，从而判断这次跑批是否在正常推进、是否卡死或大面积超时。
- **优先级**：`P0`（`已确认`）
- **理由**：跑批可能持续数分钟且消耗成本；没有进度反馈，用户会盲等或重复发起，直接放大成本。
- **依赖**：US-006
- **备注**：工程规则 §5 明确禁止用前端写死 Mock 冒充跑批进度。

### US-008 · 单次运行报告

- **故事**：作为 ROLE-A，我希望在一次跑批结束后**看到汇总报告**——总分、各算子指标、成功率、耗时 P50/P95、Token 消耗与估算成本，从而判断这一版到底是变好还是变差、贵了多少。
- **优先级**：`P0`（`已确认`）
- **理由**：核心链路的「出结论」环节。
- **依赖**：ED-06 / ED-07
- **备注**：总分聚合方式见 `product-overview.md` `OPEN-1`（**未决**），分母口径见 `OPEN-5`（**未决**）。

### US-011 · Badcase 双栏 Diff 诊断抽屉

- **故事**：作为 ROLE-A，我希望在发现某条 Case 分数低时，**点开它打开一个诊断抽屉**，在同一屏看到：Query、标准参考答案 Golden Answer、基线版本输出 vs 当前版本输出（双栏对比）、检索到的 Context 切片、以及裁判的扣分理由，从而不用在多个系统间来回切换就能判断「到底哪一步坏了」。
- **优先级**：`P0`（`已确认`）
- **理由**：这是产品定位里「直观看到具体哪条 Case 退化了」的直接兑现，也是相对普通评测工具的核心差异化。
- **依赖**：ED-07、`case_key` 对齐（见 US-009）
- **备注**：P0 版本以「同一次 EvalRun 内低分 Case 的明细」即可成立；与**已确认 baseline** 的双栏对比依赖 US-009 / US-020（P1）。若 baseline 已确认则直接显示双侧，否则单侧展示并标注「暂无基线」。

### US-015 · 多模型统一网关配置（ROLE-B 职责，但属 P0 链路前提）

> 本故事归属 **ROLE-B**，因它是整条 P0 链路的物理前提，故前置在 ROLE-A 章节一并说明。

- **故事**：作为 ROLE-B，我希望**配置模型厂商凭证**（API Key 掩码保存、模型列表、输入 / 输出千 Token 单价、并发上限），从而使平台内的 T1 调用与成本核算有据可依。
- **优先级**：`P0`（`已确认`，**首版最小范围**：单厂商至少可用 + Key 加密存储 + 单价可配）
- **理由**：虽归属 ROLE-B，但它是**整条 P0 链路的物理前提**——没有凭证，US-005/006 一步都走不了。因此必须计入 P0，但可只做最小闭环。
- **依赖**：无
- **备注**：P0 只做**最小闭环**——至少一个厂商可用、Key 加密存储、输入 / 输出千 Token 单价可配。多厂商路由、分时单价、限流策略等完整形态在 P1 内扩展，不另立编号。

## 3. ROLE-B · 平台管理员 / QA 负责人

> 下列故事中，**US-015 已计入 P0 闭环**（因其是被测执行的前提，故在 ROLE-A 章节前置说明），其余按效率价值排序。

### US-009 · 双版本 / 多模型评测报告对比

- **故事**：作为 ROLE-A / ROLE-B，我希望**任选两次 EvalRun 并排对比**——总分与各项指标的涨跌、耗时 P50/P95 变化、Token 成本变化，并以`case_key` 对齐逐条结果标出「变好 / 变差 / 持平」，从而用数据拍板「这一版能不能上」。
- **优先级**：`P1`（`已确认`）
- **理由**：P0 已有单次报告与低分 Case 明细，可以回答「这次多少分、哪条差」；跨版本对比回答的是「比上次好还是差」，价值高但可先用两次单报告人工比对过渡。
- **依赖**：US-008、`case_key` 稳定（ED-03）

### US-010 · Badcase 筛选与排序

- **故事**：作为 ROLE-A，我希望在结果列表里**按得分区间、算子、是否退化、是否失败（超时 / 解析失败）来筛选排序**，从而在几百条 Case 中快速锁定最该看的那几条。
- **优先级**：`P1`（`已确认`）
- **理由**：P0 可退化为「按分数升序展示失败项」；多维筛选是规模化后的效率增强，不阻断闭环。
- **依赖**：US-008、US-009（「是否退化」需对比）

### US-013 · 提名 Baseline

- **故事**：作为 ROLE-A，我希望在某个 EvalRun 结果不错时**把它「提名」为该评测集的候选基线**，并附一句说明，从而让团队对「以哪次为准」形成明确待审清单。
- **优先级**：`P1`（`已确认`）
- **理由**：BL-1 规定研发只能提名、管理员确认；提名本身在 P0 无消费方（P0 不计算退化率），故随 US-020 一起进 P1。
- **依赖**：US-008、`product-overview.md` §5

### US-014 · 中止进行中的 EvalRun

- **故事**：作为 ROLE-A，我希望发现跑批配置错了（选错版本、算子参数写错）时**能立即中止**，从而不再继续烧 Token。
- **优先级**：`P1`（`已确认`）
- **理由**：P0 可用「控制并发数 + 小样本先跑」规避；中止是成本安全阀，价值明确但非链路必需。
- **依赖**：US-006

### US-016 · 全局标准算子模板管理

- **故事**：作为 ROLE-B，我希望把团队认可的算子配置（如「忠实度裁判 v2」「Recall@10 检索评测」）**存为全局模板**，从而让研发不用每次重写 Prompt、也保证全团队口径一致。
- **优先级**：`P1`（`已确认`）
- **理由**：P0 允许在 EvalRun 内直接配置算子实例；模板解决的是「口径统一 + 复用」，是规模化的效率问题。
- **依赖**：US-003 / US-004

### US-017 · CI/CD Webhook 回归门禁规则配置

- **故事**：作为 ROLE-B，我希望配置**门禁规则**（如「P0 评测集得分 < 0.85」或「相对已确认 baseline 退化 > 5%」则判定为阻断），并把规则绑定到某个评测集 + Target，从而让回归门禁成为可执行的客观标准。
- **优先级**：`P1`（`已确认`）
- **理由**：价值极高但完全依附于 P0 的跑批结果与 P1 的 baseline（BL-2 规定退化永远相对已确认 baseline）。前置未完成时它无从计算。
- **依赖**：US-006、US-008、US-020

### US-018 · 门禁结果推送（飞书 / 企微 / GitHub PR）

- **故事**：作为 ROLE-B，我希望评测结束后把**结论与阻断信号推送到团队现有协作渠道**（飞书 / 企微 / GitHub PR 评论），从而让研发在写代码的地方就能收到回归结论。
- **优先级**：`P1`（`已确认`）
- **理由**：是 US-017 的呈现层；无推送也可由管理员在平台内查看结论，故不构成闭环阻塞。
- **依赖**：US-017、US-021（若需 PR 触发）

### US-019 · 全局 Token 消耗台账

- **故事**：作为 ROLE-B，我希望按**时间、模型、评测集、发起人**维度查看 Token 消耗与费用汇总，并能下钻到具体 EvalRun，从而回答「这个月评测花了多少钱、谁花的、能不能省」。
- **优先级**：`P1`（`已确认`）
- **理由**：属「成本对账」，正是 P1 定义中的效率项。P0 需在单次报告里就落库 Token 与成本字段（ED-07），台账只是聚合视图，故不应反过来阻塞 P0。
- **依赖**：US-008（单次成本必须已落库）

### US-020 · 确认 Baseline

- **故事**：作为 ROLE-B，我希望对研发提名的候选基线**做确认或驳回**，确认后它成为该评测集的比较基准，从而让后续所有「退化率」计算有一个不会被随手改动的锚点。
- **优先级**：`P1`（`已确认`）
- **理由**：BL-1 / BL-3 的制度落点；US-017 门禁的硬前提。
- **依赖**：US-013、`product-overview.md` §5

### US-021 · 接入外部 HTTP Target（T2）

- **故事**：作为 ROLE-A，我希望在要评**已部署的 RAG / Agent 应用**时，**把 Target 配成一个 HTTP 端点**（URL、鉴权、请求 / 响应字段映射），平台发 query、收 answer 与检索切片，从而把评测对象从「平台内 Prompt」扩展到「真实线上链路」。
- **优先级**：`P1`（`已确认`）
- **理由**：需求方已拍板「架构按 T3、落地 T2 放 P1」。真正评 RAG 检索策略必须靠它，但首版要保证零外部依赖。
- **依赖**：US-005（Target 抽象）、`product-overview.md` §4
- **备注**：若端点不回传 Token 用量，成本记为 `unknown`，**不得用估算值冒充真实成本**。

## 4. P2 · 仅留字段不做界面

### US-012 · Badcase / 线上 Trace 一键回流为新版本评测集

- **故事**：作为 ROLE-A，我希望把线上出错的真实 Trace 或本次跑批的低分 Badcase **一键勾选回流**，生成该评测集的新版本草稿，从而让评测集随真实问题持续进化。
- **优先级**：`P2`（`已确认`）
- **理由**：P0 的「新建版本」能力已能完全覆盖同等效果——手工整理成 JSONL 再导入即可，回流只是把这一步自动化；且「线上 Trace」在首版并无数据源接入。属自动化增强而非能力缺口。
- **依赖**：US-001、US-008

> 其中「人工盲评打榜」按 P2 标准处理：**仅保留底层字段扩展性，不做界面**。

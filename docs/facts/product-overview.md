## 1. 产品定位（已确认）

**Evaluation Middle Platform** 是一个企业级 AI 评测中台，服务于大模型应用、RAG 与 Agent 研发团队的**批量评测与版本对比**。

### 1.1 核心目标（已确认）

团队在修改 **Prompt**、**RAG 检索参数** 或 **切换底层大模型** 后，能在 **3 分钟内**发起一次量化的基准回归评测，并直观看到：

1. **总分升降**；
2. **成本变化**；
3. **具体哪条 Case 退化了**（Badcase Diff）。

### 1.2 核心闭环（已确认）

```
导入评测集（不可变版本快照）
   → 配置算子（确定性规则算子 + LLM-as-a-Judge 裁判算子）
   → 创建评测实验 EvalRun（评测集版本 × 待测目标 × 算子组合）并发执行
   → 实时查看进度与单条耗时
   → 查看总分 / 指标 / 耗时 / Token 成本
   → 与已确认 baseline 对比，逐条 Badcase Diff 定位退化原因
```

三个**不可让渡**的产品特性（任何改动不得削弱）：

| 编号 | 特性 | 含义 |
|---|---|---|
| PT-1 | 可追溯 | 任何一个历史分数都能反查出：用的是哪个**评测集版本**、哪套**算子参数**、哪个**模型/目标** |
| PT-2 | 不可变 | 已发布的评测集版本、已完成的 EvalRun、已产出的 CaseResult 均不可修改 |
| PT-3 | 可对比 | 任意两次 EvalRun 的**总分与逐条结果**可对齐比较，且对齐依据是稳定的 `case_key` |

## 2. 用户角色（已确认 · 极致收敛为 2 个）

> **角色收敛原则**：每多一个角色，权限与界面复杂度翻倍。首版只设 2 个角色。

### ROLE-A · AI / 算法研发工程师（核心高频使用者）

**定位**：评测中台的主要使用者，负责「出题—跑批—看结果—查退化」全流程。

**职责边界（已确认）**：

- 上传与维护评测集（导入即产生不可变版本快照）；
- 配置评测算子（确定性规则算子 + LLM-as-a-Judge 裁判算子）；
- 发起不同版本 Prompt / RAG 参数 / 模型路由的评测跑批；
- 实时查看跑批进度与单条耗时；
- 对比两个版本的指标涨跌；
- 在 Badcase Diff 抽屉中排查退化原因；
- **可「提名」baseline，但无权确认**（见 §5）。

**明确不具备**：配置模型网关凭证与单价、管理全局算子模板、配置 CI/CD 门禁阈值、确认 baseline。

### ROLE-B · 平台管理员 / QA 负责人（基础设施与门禁管理者）

**定位**：负责「钱、钥匙、闸门」三件事，不参与日常评测内容的制作。

**职责边界（已确认）**：

- 配置多模型网关凭证（API Key、并发限流、分时 / 模型单价表）；
- 管理全局标准评测算子模板；
- 配置 CI/CD Webhook 回归门禁阈值（例：P0 评测集得分低于 `0.85`，或相对 baseline 退化超 `5%`，则阻断报警）；
- 审计全局 Token 消耗台账；
- **确认 baseline**（研发只能提名）。

### 2.1 权限矩阵（已确认）

| 能力 | ROLE-A 研发工程师 | ROLE-B 平台管理员 |
|---|---|---|
| 导入评测集 / 新建版本 | ✅ | ✅ |
| 查看评测集与版本 | ✅ | ✅ |
| 配置算子实例（在 EvalRun 内） | ✅ | ✅ |
| 管理**全局**算子模板 | ❌ | ✅ |
| 发起 EvalRun | ✅ | ✅ |
| 查看进度 / 报告 / Badcase Diff | ✅ | ✅ |
| 提名 baseline | ✅ | ✅ |
| **确认** baseline | ❌ | ✅ |
| 配置模型网关凭证与单价 | ❌ | ✅ |
| 配置 CI/CD 门禁阈值 | ❌ | ✅ |
| 查看全局 Token 消耗台账 | ❌（仅看单次运行成本） | ✅ |

### 2.2 工作区与权限模型（已确认）

- **单工作区、全团队共享**，不做 per-dataset 授权，不做多租户。
- 表中**预留** `workspace_id` / `owner_id` 字段，**首版不启用任何权限控制**，仅作数据归属记录。
- 不做复杂 RBAC、不做项目空间隔离、不做审批流。

## 3. 首版「不做清单」（已确认）

> 以下为**明确拒绝**的首版范围。写入此处以避免后续反复讨论。

| 编号 | 不做项 | 拒绝理由 |
|---|---|---|
| OUT-1 | 外包标注员独立端 | 首版评测集由研发直接供给，不存在标注流水线 |
| OUT-2 | 财务审批 / 预算流 | 成本只需**可查、可归因**，不需要审批链 |
| OUT-3 | 只读高管大屏 | 运行报告页已覆盖该信息，独立角色只增权限不改价值 |
| OUT-4 | 复杂 RBAC / 多租户 / 项目空间 | 2 角色 + 全共享足够；字段预留、功能不做 |
| OUT-5 | 多人协同人工盲评打榜 | 属人工评测体系，与自动评测同版会污染数据模型（仅留底层字段扩展性） |

## 4. 待测目标 Target 的执行方式（已确认）

### 4.1 架构按 T3 设计，落地按 T1 → T2 分阶段

| 代号 | 方式 | 描述 | 里程碑 |
|---|---|---|---|
| **T1** | 平台内执行 | 平台保存 Prompt 模板 + 变量，自行调用模型网关取得输出，平台负责算子计算 | **P0（首版）** |
| **T2** | 外部 HTTP 回调 | 调用已部署应用的 HTTP 端点，收 answer + 检索切片 + 耗时，平台负责算子计算 | **P1（接入）** |
| **T3** | 两者都支持 | 统一的 Target 抽象，两种执行器并存 | **架构设计目标** |

**定案依据（已确认）**：

- 首版只做 T1，保证**零外部依赖、可离线演示、Token 成本 100% 精确归因**；
- 架构层按 T3 抽象，T2 只增执行器、不改数据模型，为后续评 RAG / Agent 留接口；
- 选 T2 时 Token 成本改由端点上报，端点不报则记为 `unknown`，不得用估算值冒充真实成本。

### 4.2 Target 快照规则

Target 必须**带版本**，并在发起 EvalRun 时**快照**进该次运行。后续修改 Prompt 模板或模型配置，**不得影响历史 EvalRun**（与 PT-2 一致）。

## 5. Baseline 认定权（已确认）

| 编号 | 规则 |
|---|---|
| BL-1 | **Baseline 由 ROLE-B 管理员确认**，ROLE-A 研发只能「提名」 |
| BL-2 | 门禁中的「退化超 N%」**永远相对已被确认的 baseline 计算** |
| BL-3 | 研发不得自行指定基线，防止挑一个跑崩的历史结果来「通过」门禁 |
| BL-4 | 更换 baseline 只改变「当前指向」，**不覆盖任何历史 EvalRun 记录** |

## 6. 领域实体边界（已确认 · 不可混用）

> 本表是防止「静态评测集 Dataset」与「单次运行快照 EvalRun」混淆的硬约束。

| 编号 | 实体 | 是什么 | 可变性 |
|---|---|---|---|
| ED-01 | **Dataset** | 评测集逻辑容器（一个名字、一个用途） | 名称 / 描述可变 |
| ED-02 | **Dataset Version** | 某次导入产生的**完整条目快照** | **绝对不可变**；改 = 新建版本 |
| ED-03 | **Case** | 版本内一条样本（query + 参考答案 + 检索标注） | 随所属版本**冻结** |
| ED-04 | **Operator** | 算子定义（规则 / 裁判 + 参数 + 阈值） | 全局模板可改；**引用时快照**进 EvalRun |
| ED-05 | **Target** | 待测对象（Prompt + 模型组合，或外部 HTTP 端点） | 带版本；**跑批时快照**进 EvalRun |
| ED-06 | **EvalRun** | 一次跑批 = 数据集版本 × Target 快照 × 算子快照 × 时间 | **不可变**；重跑 = 新建 EvalRun |
| ED-07 | **CaseResult** | 单条结果（输出、各算子得分、耗时、token、扣分理由） | **不可变** |
| ED-08 | **Baseline** | 被正式指定为该评测集比较基准的某一次 EvalRun | 可改「指定」，历史不被覆盖 |

### 6.1 不可变红线（已确认）

1. **Dataset Version 发布后不可变**，严禁原地增删改 Case；任何变更都是**新建版本**。
2. 不原地删除 Case：否则历史 EvalRun 的逐条结果会指向不存在的 Case（破坏 PT-1 / PT-3）。
3. **EvalRun 与 CaseResult 不可变**，重跑产生新 EvalRun，不覆盖旧的。
4. 任何一个「昨天 0.82、今天 0.91」的对比，都必须可反查到两个不同的 EvalRun 及其各自的 Dataset Version、算子参数、模型配置。

## 7. Dataset Version 最小完备契约（已确认）

> 这是 P0 三个检索算子（Recall@K / MRR / nDCG@K）与逐条 Badcase Diff 能否成立的**前提**。
> 表结构定稿见后续 `docs/facts/database-schema.md`；此处只锁定**字段语义与必填性**。

### 7.1 Case 字段（已确认）

| 字段 | 必填 | 语义 |
|---|---|---|
| `case_key` | ✅ | **业务唯一键**，跨版本对齐的唯一依据。缺省 = 规范化 `input` 的 hash，导入者可显式覆盖 |
| `input` | ✅ | 待测 query；可选 `history` 等变量 |
| `reference` | 可选 | `golden_answer`（裁判 / 精确匹配用）、`reference_facts`（数值保真用） |
| `retrieval` | 可选 | `relevant: [{doc_id, grade}]` —— **Recall@K / MRR / nDCG@K 的唯一依据** |

### 7.2 Dataset Version 字段（已确认）

| 字段 | 必填 | 语义 |
|---|---|---|
| `version_no` | ✅ | 单调递增，不可变 |
| `schema_version` | ✅ | **首版固定为 `"1"`**，不可变 |
| `case_count` | ✅ | 条目数 |
| `content_hash` | ✅ | 内容指纹，用于判断两次导入是否等价 |
| `source` | ✅ | `import` / `mine` / `回流` |
| `created_by` / `created_at` | ✅ | 创建人与时间 |

### 7.3 两条硬约束（已确认）

1. **没有 `retrieval.relevant`，Recall@K / MRR / nDCG@K 无法成立**（只能算 0 或无法验证），而这三个算子属 P0。
2. **没有稳定的 `case_key`，v1 的 Case 在 v2 中无法对齐**，「哪条退化」将退化为人工比对，Badcase Diff 直接失效。
3. `schema_version` 首版就必须落库。缺省的补救成本最高，不允许「先不建、以后再补」。

### 0.1 联调暴露并修复的两个真缺陷

| # | 现象 | 根因 | 修复 |

| 1 | worker 在空队列上以 200ms 节奏无限刷 `[worker] 领取 run null（null 条 Case）` | `claim_next_run()` 声明为 `RETURNS eval_runs`（**复合类型**）。PL/pgSQL 返回「无行」时，`SELECT * FROM claim_next_run()` **仍是一行**，只是字段全 NULL ⇒ `queryOne()` 判不出空 | `0017_queue_functions.sql` 改为 `RETURNS SETOF eval_runs` + `IF r.id IS NULL THEN RETURN`；`tests/queue.spec.ts` 5 条用例钉死（含「SQL 层本身必须零行」「领取后队列变空再返回 null」「FIFO」） |

```
                  id                  |     name     |  status   | total_cases | succeeded_cases | failed_cases | score_overall | pass_rate | coverage | cost_total | created_by
--------------------------------------+--------------+-----------+-------------+-----------------+--------------+---------------+-----------+----------+------------+------------
```

- `cost_total = 0.00000000` ⇒ `GENERATED ALWAYS AS (cost_target + cost_judge) STORED` 由数据库算出。

## 9. 补测 #6：心跳租约（方案 A）

### 9.1 缺陷与修复

原判据 `started_at < now() - p_stale_after` 会让任何**耗时超过阈值**的正常 run 被另一个 worker
当成僵尸回收并二次执行。行级幂等（`UNIQUE(eval_run_id, case_key)`）挡得住重复**结果行**，
挡不住重复的**网关调用** —— 真网关下即重复计费，而 `cost_target` 只记一次。

修复（`0018_heartbeat_lease.sql` + `worker/loop.ts`）：

- `eval_runs.heartbeat_at timestamptz`（可空）；
- 回收判据改为 `GREATEST(started_at, heartbeat_at) < now() - p_stale_after`，
  `heartbeat_at IS NULL` 时 PG 忽略 NULL 自动回退到 `started_at`（T-13/T-14 语义不变）；
- worker 在处理期间按 `WORKER_STALE_AFTER / 3` 续约（10 minutes ⇒ 200s），间隔与 TTL 均从配置派生；
- 回收时同步清空 `started_at` 与 `heartbeat_at`；
- down 脚本 `db/migrations/down/0018_heartbeat_lease.down.sql`（非递归扫描 ⇒ 不被 `migrate()` 执行），
  `tests/heartbeat.spec.ts` H-03 在**影子库**里验证「前滚 → 回滚 → 再前滚」。

### 9.2 对抗场景实测（STALE_AFTER=1s，单 Case 6s，双 worker 进程）

```
[H-10] lease=1 second caseDelay=6000ms cases=2 heartbeat=2026-11-09T10:47:46.700Z
       gatewayHits=[1,1] claimLines=1 reclaimLines=0 frozenLines=0 duration≈7248ms
[H-11] killedAfterHeartbeat=true statusAfterKill=RUNNING gatewayHits=[2,2]
       reclaimLines=1 resultRows=2 duration≈8792ms
[H-12] runningSamples=[0,1,2] midValues=110 finalSucceeded=3 duration≈18950ms
 Test Files  1 passed (1)
      Tests  3 passed (3)
```

- **同一 run 不被二次领取**：`claimLines=1`；
- **网关请求数 = Case 数 × 1**：`gatewayHits=[1,1]`（心跳持续时，`reclaimLines=0`）；
- **收尾不再出现** `is terminal (COMPLETED), row is frozen`：`frozenLines=0`。

## 10. M2 待办（合并说明单列，**不混进 #6 修复**）

| # | 待办 | 说明与建议 |
|---|---|---|
| M2-1 | **at-least-once 语义下的重复计费** | #6 修好的是「**正常**长任务不被抢占」。worker **真崩溃**时，回收方会重跑崩溃瞬间**在途**的 Case（H-11 实测 `gatewayHits=[2,2]`：两条 Case 都已在途时被杀）。结果行仍幂等（`resultRows=2`），但**网关被多调用一次**，`cost_target` 与实际账单可能不一致。选项：① 网关侧幂等键去重（请求带 `run_id + case_key` 派生的 idempotency key，由网关保证只计费一次）；② 接受重复计费并在报告里标注「该 run 发生过回收」。**建议 ①**，因为 `cost_target` 是产品承诺的读数，不能只做到「接近」。这一条不应被 #6 的通过掩盖。 |
| M2-2 | **测试库与 dev 库共用同一实例** | 当前测试通过 `dropAndRecreateSchema` 直接重建 `public` schema，与 dev 数据同实例。建议：独立 database（最彻底，连接串可完全隔离）或独立 schema（成本低，但 `search_path` 与迁移脚本需同时支持）。**建议独立 database**。 |
| M2-3 | **租约没有 fencing token（方案 A 的固有局限）** | 回收只在「心跳过期」时发生；若原 worker 只是**长时间停顿**（GC / 宿主挂起）而非死亡，它恢复后会继续续写心跳，把已被别人领走的 run 重新「点亮」。此时两个 worker 可能同时在跑同一条 run。彻底解法是给每次领取分配单调递增的 `claim_epoch`，写入结果与心跳都带 `WHERE claim_epoch = $epoch`，旧属主的所有写入自动失效。**建议 M2 落地**；M1 场景（进程被杀 / 容器重启）下心跳会随进程一起消失，本条不会触发。 |

## 12. 环境坑（本次实测踩到，非产品缺陷）

`next build` 与 `next dev` **不能对同一个 `.next` 目录并行**。本轮 `#3 next build` 跑过一次之后，
那个还活着的 `next dev`（:3000）把 `.next/app-build-manifest.json` 覆写成 dev 版（引用无 hash 的
`main-app.js`），而 `static/chunks/` 里只剩 build 产出的 hash 文件 ⇒ `main-app.js` / `polyfills.js` /
`layout.css` 全部 404，页面永远停在 SSR 的「加载中…」。

排查证据：

```
--- static probe ---
404 len=9  /_next/static/chunks/main-app.js
404 len=9  /_next/static/chunks/polyfills.js
404 len=9  /_next/static/css/app/layout.css
200 len=2619352 /_next/static/chunks/app/runs/%5BrunId%5D/page.js
200 len=141135  /_next/static/chunks/webpack.js
```

结论：**这是环境状态问题，不是页面缺陷**。`npm run build` 后重启 `next start` 即恢复，
浏览器四条验收随后全绿。建议把「构建前先停 dev server」写进 M2 的开发者脚本
（`dev-all.ts` 里可在 `build` 前置检查 3000 端口）。

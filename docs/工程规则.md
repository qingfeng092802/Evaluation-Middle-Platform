# 工程规则与 MCP / Skills 调度规范

> **本文件是全项目工程规则与 MCP / Skills 调度的唯一正文。**
> 其他任何文件（`README.md`、`AGENTS.md`、`CLAUDE.md`、各 SPEC）凡涉及工程规则，
> 一律**引用本文件**（`docs/工程规则.md`），不得抄写副本。
> 规则变更只在本文件进行；发现冲突时先指出具体条目，经确认后再改。

---

## 1. 单一事实源原则

同一项产品设定、评测指标公式、接口或数据规则**只在一处维护**。

| 内容类型 | 唯一责任位置 |
|---|---|
| 产品定位、用户故事、页面流程、技术方案、数据表结构、视觉规范 | `docs/facts/` 下对应的单一文档 |
| 里程碑与任务规格 | `docs/Spec/milestones.md`、`docs/Spec/SPEC-*.md` |
| 可编译的接口 / 数据契约 | `src/contracts/` |
| 工程规则、MCP / Skills 调度 | 本文件 |

- 其他地方通过**链接 + 稳定编号**引用（如 `US-001`、`M1`、`SPEC-M1`），绝不重复抄写。
- 事实发生变化时，**只更新原责任文档**，再由引用方链接生效。
- 修改产品设定 / 指标公式 / 接口 / 数据规则时，必须**同步更新对应责任文档与 `src/contracts/` 契约**。
- 发现两处内容冲突时，先指出冲突的具体内容，与需求方确认后再修改，不自行裁决。

---

## 2. 分支隔离与基线稳定

- `src/` 主分支 `main` 保持**绝对稳定**，任何未经验收的改动不得直接提交到 `main`。
- 每项开发从**已确认的基线**（`main` 的确认提交）创建独立任务分支。
- 多模块正交开发时使用 `git worktree` 隔离，避免互相污染工作区。
- 开发与自检均在任务分支上完成。

---

## 3. 契约与 SPEC 先行

- 开发前**必须先确认**对应的 SPEC（`docs/Spec/SPEC-*.md`）以及 `src/contracts/` 中的接口 / 数据契约。
- 已经存在的代码和组件，先检查**是否可以复用**，复用优先于新建。
- 不顺便修改与本次任务无关的功能。

## 4. TDD 与评测算子精度门禁

- 编码遵循 `obra/superpowers` 的测试驱动开发：**先写验证测试（Red）→ 再写最小实现（Green）→ 最后重构（Refactor）**。
- 评测算子必须有**确定性的黄金输入输出单元测试**覆盖，至少包括：
  - `Recall@K`
  - `MRR`
  - `nDCG@K`
  - JSON Schema 校验
  - 数值保真度校验
  - LLM-as-a-Judge 结果解析
- 提交代码必须通过：**类型检查** + **Linter** + **测试门禁**。
- Linter 必须包含**禁止在业务组件中裸写未定义的 `#hex` 色值**（颜色必须走 Tailwind Token / CSS 变量）。
- **严禁**通过删除或弱化测试断言来让测试通过。

### 4.0 构建产物门禁（`B-01`/`B-02` 复盘，2026-11-09）

> 事故现象：`/api/datasets` 返回 3 条，页面却显示「还没有评测集」。根因不在页面代码，
> 在 `.next`：一次 `next build`（生产）与一个还活着的 `next dev` 把两套 chunk 命名规则
> 写进了同一个目录（`BUILD_ID` 是 18:34 的生产构建，`static/development/` 是 19:09 的 dev），
> `main-app.js` / `polyfills.js` / `layout.css` 全部 404 ⇒ 没有客户端 JS ⇒ 不水合
> ⇒ `useApi` 拉回的数据永远进不了表格。

由此产生三条硬规则：

- **构建前必须停掉 dev server。** `npm run build` 的 `prebuild` 会跑
  `scripts/check-next-artifacts.ts`：产物指纹不一致、或有 next 进程在写 `.next`，一律拦截（退出码 1）。
- **`dev:all` 启动前同样要过产物检查。** 只有生产 `BUILD_ID`、还没有 dev 产物的目录直接起
  `next dev` 也会混（dev 不会清掉 `BUILD_ID`），所以 `dev:all` 比 `prebuild` 多拦这一条。
- **清理 `.next` 用 `npm run clean:next`，不要 `rm -rf`。** 在活着的 dev 底下删 `.next`
  会把 dev 一起弄坏，症状与混合产物完全相同；该脚本会先确认没有 next 进程在写，确认不了就拒绝。

对应回归测试：`tests/next-artifacts.spec.ts`、`tests/data-table-render.spec.ts`、
`tests/dev-all.spec.ts`。

**第四条硬规则：合并前必须手动跑一次 `npm run check:datasets-render`。**

这条检查**接不进自动门禁**，原因是结构性的，不是疏漏：

- 仓库当前**没有 CI 工作流**（无 `.github/workflows/`），`pre-commit` 钩子只跑
  `typecheck` / `lint` / `test` 三道机械门禁；
- 而它需要**一个真实在跑的 `next dev`** 和一个真实浏览器（Edge + npx 缓存里的
  `playwright-core`，不新增 devDependency）。`pre-commit` 里没有服务在跑，
  把它挂上去只会得到 `ECONNREFUSED`，然后被人加 `--no-verify` 绕过 ——
  那比不挂更糟。

所以它的定位是**人工合并门禁**：

```bash
npm run dev:all            # 另开一个终端，等服务起来
npm run check:datasets-render          # 默认 http://127.0.0.1:3000
# 或指定端口：npx tsx scripts/check-datasets-render.ts http://127.0.0.1:3100
```

退出码 0 = 接口条数与渲染行数一致；非 0 会打印 `ROWS_MISMATCH` / `STATUS_MISMATCH`
并把截图写到 `docs/Spec/screenshots/b02-render-mismatch.png`。

> **独立验收必须跑这条。** 单元测试只能证明「`DataTable` 给 N 条会渲染 N 行」，
> 证明不了「真实页面上水合没坏」。2026-11-09 的事故里每一层单测都是绿的，
> 只有这条跨层对账能抓住。

### 4.1 前端样式与数字排版硬门禁（阶段 03 定稿）

> 视觉语义的事实源是 [`docs/facts/DESIGN.md`](./facts/DESIGN.md)。本节只规定**门禁如何执行**，不重复 Token 值。

**三条禁令（DESIGN §7.1 的 `AS-1` / `AS-2` / `AS-3`）**：

| 编号 | 禁令 | Linter 载体 |
|---|---|---|
| `AS-1` | 严禁大面积紫粉 / 蓝紫霓虹渐变、光晕、玻璃拟态 | ESLint `no-restricted-syntax` 匹配 `gradient(` 字面量 |
| `AS-2` | 严禁在 `.tsx` / `.jsx` / `.css`（`globals.css` 除外）中硬编码裸 `#hex`、`rgb()` / `hsl()` 字面量或内联 `style={{}}` | ESLint 匹配 `Literal[value=/^#[0-9a-fA-F]{3,8}$/]` 与 `JSXAttribute[name.name='style']`；stylelint `color-no-hex` |
| `AS-3` | 任何数据表格必须有真实空状态、`Skeleton` 骨架、超长文本截断 + 一键复制 | 验收清单逐项人工核对（无法静态检查） |

**数字排版强制令**：

- **所有指标分数、耗时、Token 数、金额、计数所在的表格列、指标卡、徽章、坐标轴刻度，一律使用 `tabular-nums`（并同时 `slashed-zero`）。**
- 无「大字号例外」：`DESIGN.md` §3.2 已记录该条对 `dataviz` 技能默认建议的**知情偏离**，理由是 SSE 实时值跳动会导致指标卡横向抖动。
- 数字列默认右对齐；数字格式必须统一（见 `DESIGN.md` §3.3），否则 `tabular-nums` 对齐不成立。

**离线与资源禁令**（与 §9 一致）：

- 禁用 `next/font/google`；字体必须经 `next/font/local` 或 npm 包本地打包。
- 禁止任何 CDN 版字体 / 图标 / 图表资源；禁止深引 `lucide/dist`。
- ECharts 主题必须从 Token 生成一次（`lib/charts/theme.ts`），**禁止在 `option` 里写裸 `#hex`**。

**补充脚本**：`npm run check:tokens` —— 扫描 `.tsx` 中的 `rgb(` / `hsl(` / 6 位 hex / `gradient(`，CI 必跑。

### 4.2 测试库隔离（`B-03`/`B-04` 复盘，2026-11-10）

> 事故现象：独立验收跑全量时，`heartbeat-worker.spec.ts` 的 H-10/H-11 间歇性失败 ——
> `expected [2,2] to deeply equal [1,1]`（网关被打了两次）、
> `超时 15000ms 未等到：A 领取 run`。
>
> 根因不在断言，在**测试与常驻 worker 共用同一个库** `eval_platform`：
> 测试 `beforeAll` 里 `dropAndRecreateSchema()`，而 `dev:all` 的 worker 正在同一队列上
> 每 200ms 轮询 `claim_next_run()`。测试刚插入的 PENDING run 被常驻 worker 领走，
> 两边各跑一遍同一个 Case ⇒ 网关请求翻倍、领取日志出现两条。

由此产生三条硬规则：

- **真库测试一律连 `eval_platform_test`。** `vitest.config.ts` 的 `setupFiles` 指向
  `tests/setup/test-env.ts`，它在每个测试进程启动时把 `process.env.DATABASE_URL`
  改写成测试库（库名 = dev 库名 + `_test`，不存在则自动 `CREATE DATABASE`）。
  被测代码无需任何改动 —— 它们读的都是 `process.env.DATABASE_URL`。
- **配错必须当场炸。** `assertIsolatedTestDatabase()` 在测试库与 dev 库同名时抛错，
  而不是跑出随机超时（随机失败最容易被误判为 flaky）。
- **`dev:all` 不得连测试库。** `assertDevDatabase()` 在库名以 `_test` 结尾时拒绝启动 ——
  隔离是双向的，少了这一边，事故只是换了个方向重演。

**为什么是独立 database 而不是独立 schema**：`dropAndRecreateSchema()` 执行的是
`DROP SCHEMA public CASCADE`，它清的就是 `public`；只隔 schema 仍会打到 dev 数据。
独立 database 是唯一能保证这条语句只影响测试的隔离级别。

对应回归：`tests/test-db.spec.ts`（派生规则 + 配错拦截 + **本进程真的落在测试库**，
摘掉 `setupFiles` 接线即变红）、`tests/dev-all.spec.ts` 的 `assertDevDatabase` 组。

> **这一条不改变任何断言。** H-10 的 `gatewayHits=[1,1]`、H-11 的超时阈值都原样保留，
> 修的是测试环境，不是测试标准。

### 4.3 夹具不变量与收尾复原（`B-07`/`B-08` 复盘，2026-11-10）

> 事故现象：dev 库里 10 个数据集全部显示「样本数 1」、点进去一行都没有；
> 10 个 Target 全部是 `current_version_no=0` 却挂着 v1；厂商 `base_url` 为 NULL。
> 种子里明确写「不种 Target、不种 Run」，所以这些都不是种子留下的。

根因是 `tests/queue.spec.ts` 的夹具手写 SQL 直插，绕过了 `db/repo/*`：

| 声明列 | 真实数据 | 缺陷写法 |
| --- | --- | --- |
| `dataset_versions.case_count` | `dataset_cases` 行数 | 写死 1，一条都不插 |
| `targets.current_version_no` | `max(target_versions.version_no)` | 用默认值 0，却插了 v1 |
| `model_providers.base_url` | 被 Target 引用时必须可调用 | 不写，留 NULL |

收尾也只 `closeDb()`，没有复原 —— 残渣一路留到下一次人工点页面才被发现。

由此产生两条硬规则：

- **夹具必须自己维持 repo 层的不变量。** 声明几行就插几行，挂了版本就把
  `current_version_no` 推上去，被引用的厂商必须带 `base_url`。
  共享夹具集中在 `tests/support/fixtures.ts`，不允许各 spec 各写一份。
- **真库 spec 收尾一律复原种子。** 调 `restoreSeed()`（`tests/support/fixtures.ts`）：
  `dropAndRecreateSchema` → `migrate` → `resetDatabase` → `runSeed`，
  把库还原成「只有种子」的状态。下一个 spec 与独立验收看到的库都是可预期的。
  调用前必须先关掉自己的连接/连接池，否则 `DROP SCHEMA` 会被占用阻塞。

不变量的**体检函数**在 `tests/support/db-integrity.ts`（`allIntegrityViolations()`），
回归在 `tests/seed-integrity.spec.ts`：断言直接查数据库的行，
不是查仓储函数的返回值 —— `createVersion()` 返回的对象再漂亮，
只要没真写进 `dataset_cases`，这条一样红。

> 判据是**库里的行**，不是 API 响应或页面文本。`B-07`/`B-08` 当初之所以没被抓住，
> 正是因为全程只看「接口返回了 N 条」，没人去数 `dataset_cases` 到底几行。

## 5. 研发自检与三层真栈独立验收分离

**研发侧自检**（开发 Agent 完成后交付）：

- 交付明确的提交（commit SHA）与自检结果。
- 至少覆盖 **L1 单元测试** 与 **L2 真实数据库 / SSE 流切片验证**。
- **严禁**用纯前端写死的 Mock 数据冒充「评测跑批完成」。

**独立验收侧**（独立测试验收 Agent，针对同一份固定提交）：

- L1–L3 核验。
- 四类缺陷扫描：**韧性、横切一致性、防御编码、数据迁移**。

两侧使用**同一份 SPEC**，分别检查「实现」与「验收结果」。

## 9. 安全与凭据约束（不可协商）

- **不通过 MCP 中转数据库连接**：数据库迁移与测试直接走终端命令 / ORM。
- **不在项目中配置 GitHub PAT**：代码管理走本机已有 Git 命令行。
- 厂商大模型 API Key、`.env*`、真实用户评测数据、本地 SQLite 库文件一律**不入库**（见 `src/.gitignore`）。
- 任何密钥、令牌都不得写入文档、契约、示例配置或提交信息。
- **契约层「只写不读」**：`src/contracts/` 中凭据字段（`apiKey` / `authHeader`）只允许出现在写入形状里，读取形状必须用掩码（`apiKeyMasked`）或布尔位（`hasAuthHeader`）。非对称清单集中在 `src/contracts/src/api.ts` 的 `WRITE_ONLY_FIELDS`，供安全审查对照。
- **成本单一事实源**：所有金额由本平台 `model_prices` 计算，**永不采信 LiteLLM 或任何上游网关的成本统计**。契约中因此不含任何上游 `cost` / `usage` 字段。
- **网络与离线约束**：部署须支持本地 / 内网一键拉起；依赖、UI 组件、字体、图标、图表库一律走 npm 本地包，**不得依赖 Google 专有在线服务，不得在构建期联网拉取运行时资源**。详见 `docs/facts/technical-solution.md` §0.5。
